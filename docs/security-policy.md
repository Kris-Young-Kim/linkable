## 1. 환경변수 및 비밀키 관리

### 1.1 기본 원칙

- **절대 노출 금지**: 비밀키는 절대 Git 저장소에 커밋되어서는 안 됩니다
- **최소 권한**: 필요한 최소한의 권한만 부여해야 합니다
- **정기적 로테이션**: 비밀키는 정기적으로 로테이션(rotation)되어야 합니다

### 1.2 비밀키 분류

#### 최고 수준 비밀키 (서버 전용, 절대 노출 금지)

- `SUPABASE_SERVICE_ROLE_KEY`: Supabase 서비스 역할 키

  - RLS를 우회할 수 있는 최고 권한
  - **사용 범위**: 서버 사이드 API 엔드포인트에서만 사용
  - **절대 노출**: 클라이언트 코드, 이미지, `NEXT_PUBLIC_*` 변수에 사용 금지

- `CLERK_SECRET_KEY`: Clerk 인증 서버 키

  - 사용자 인증 및 세션 관리
  - **사용 범위**: 서버 사이드에서만 사용

- `naver_SECRET_KEY`: 네이버 파트너스 API Secret Key

  - API 요청 인증에 사용
  - **사용 범위**: 서버 사이드에서만 사용

- `GOOGLE_GENERATIVE_AI_API_KEY`: Google Gemini API 키
  - AI 모델 호출에 사용
  - **사용 범위**: 서버 사이드에서만 사용

#### 중간 수준 비밀키 (공개 가능하나 제한적 사용)

- `NEXT_PUBLIC_SUPABASE_ANON_KEY`: Supabase 익명 키

  - 클라이언트에서 사용 가능하나 RLS 보안으로 제어
  - **사용 범위**: 클라이언트 및 서버 모두 사용 가능
  - **주의**: RLS 보안이 제대로 설정되어 있는지 확인

- `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`: Clerk 공개 키

  - 클라이언트에서 인증에 사용
  - **사용 범위**: 클라이언트에서만 사용

- `naver_ACCESS_KEY`: 네이버 파트너스 API Access Key
  - **사용 범위**: 서버 사이드에서만 사용 (Secret Key와 함께 사용)

#### 낮은 수준 비밀키 (공개 가능)

- `NEXT_PUBLIC_SUPABASE_URL`: Supabase 프로젝트 URL
- `NEXT_PUBLIC_APP_URL`: 애플리케이션 배포 URL
- `NEXT_PUBLIC_GA_MEASUREMENT_ID`: Google Analytics 측정 ID

## 2. 인증 및 권한 보안

### 2.1 인증 (Authentication)

#### Clerk 인증 사용

- 모든 사용자는 Clerk를 통해 인증합니다
- 인증되지 않은 사용자는 다음 경로로만 접근 가능
  - 공개 페이지 (홈, 소개, 개인정보 처리방침)
  - 정적 리소스 (이미지, CSS, JS)

#### 인증 미들웨어

- `middleware.ts`에서 모든 보호된 경로에 Clerk 미들웨어 적용
- 공개 경로는 명시적으로 허용되어야 합니다

### 2.2 권한 (Authorization) - 역할 기반 접근 제어 (RBAC)

#### 역할 정의

| 역할      | 설명          | 권한                                                   |
| --------- | ------------- | ------------------------------------------------------ |
| `admin`   | 시스템 관리자 | 모든 관리자 기능, 제품 크롤링 사용, 관리 대시보드 접근 |
| `manager` | 상담 관리자   | 상담 데이터 접근/설정, 추천 관리 IPPA 결과 접근        |
| `user`    | 일반 사용자   | 자신 상담 기록, 추천 결과, IPPA 제출 생성/접근         |

#### 기본 원칙: Deny by Default

- 역할이 명시적으로 부여되지 않은 경우, 모든 관리자 API 및 접근 데이터 API 접근 거부
- 명시적으로 허용된 역할만 접근 가능

#### API 접근 제어 매트릭스

| API 경로                    | admin | manager | user | 비고               |
| --------------------------- | ----- | ------- | ---- | ------------------ |
| `/api/admin/*`              | ✅    | ❌      | ❌   | 관리자 전용        |
| `/api/admin/products/crawl` | ✅    | ❌      | ❌   | 제품 크롤링        |
| `/api/admin/products`       | ✅    | ❌      | ❌   | 제품 관리          |
| `/api/analytics`            | ✅    | ✅      | ✅   | 사용자 데이터만    |
| `/api/consultations/*`      | ✅    | ✅      | ✅   | 사용자/해당 상담만 |
| `/api/recommendations/*`    | ✅    | ✅      | ✅   | 사용자/해당 추천만 |
| `/api/products/sync`        | ✅    | ❌      | ❌   | 제품 동기화        |

#### 구현 세부사항

1. **`verifyAdminAccess` 함수**

   - Clerk 사용자 데이터에서 `publicMetadata.role` 확인
   - `role === "admin"`인 경우만 허용
   - 그 외 모든 경우 403 Forbidden 반환

2. **사용자 데이터 접근 제어**

   - 모든 사용자 데이터 조회 시 `user_id` 또는 `clerk_id`로 필터링
   - 다른 사용자의 데이터 접근 시도 시 403 Forbidden 반환

3. **Clerk 사용자 데이터 관리**
   - 역할 변경은 관리자만 가능
   - 역할 변경 시 로그 기록
   - 역할 변경 시 프로덕션 문서화

### 2.3 사용자 데이터 및 매핑

#### Clerk와 Supabase 매핑

- Clerk `userId`를 Supabase `users.clerk_id`로 매핑
- `ensureUserRecord` 함수로 자동 생성 시 기본 `role = "user"` 부여
- 역할 변경은 관리자만 가능

#### 사용자 데이터 소유권 검증

모든 사용자 데이터 조회/수정/삭제 시

1. Clerk 인증 확인
2. Supabase users 테이블에서 해당 `user_id` 조회
3. 요청한 사용자 데이터의 `user_id`와 비교
4. 일치하지 않으면 403 Forbidden 반환

## 3. 데이터베이스 보안 및 RLS

### 3.1 Supabase RLS (Row Level Security) 보안

#### 기본 원칙

- **모든 테이블에 RLS 활성화**
- **Service Role Key는 서버 전용**
- **클라이언트는 Anon Key만 사용**

#### 테이블별 RLS 보안

##### users 테이블

```sql
-- SELECT: 자신 데이터만 조회 가능
CREATE POLICY "users_select_own" ON users
  FOR SELECT USING (auth.uid()::text = clerk_id);

-- UPDATE: 자신 데이터만 수정 가능
CREATE POLICY "users_update_own" ON users
  FOR UPDATE USING (auth.uid()::text = clerk_id);
```

##### consultations 테이블

```sql
-- SELECT: 자신 상담만 조회 가능
CREATE POLICY "consultations_select_own" ON consultations
  FOR SELECT USING (
    EXISTS (
      SELECT 1 FROM users
      WHERE users.id = consultations.user_id
      AND users.clerk_id = auth.uid()::text
    )
  );

-- INSERT: 자신 상담만 생성 가능
CREATE POLICY "consultations_insert_own" ON consultations
  FOR INSERT WITH CHECK (
    EXISTS (
      SELECT 1 FROM users
      WHERE users.id = consultations.user_id
      AND users.clerk_id = auth.uid()::text
    )
  );
```

##### products 테이블

```sql
-- SELECT: 활성화된 제품만 공개 조회 가능
CREATE POLICY "products_select_active" ON products
  FOR SELECT USING (is_active = true);
```

##### recommendations 테이블

```sql
-- SELECT: 자신 상담의 추천만 조회 가능
CREATE POLICY "recommendations_select_own" ON recommendations
  FOR SELECT USING (
    EXISTS (
      SELECT 1 FROM consultations
      JOIN users ON users.id = consultations.user_id
      WHERE consultations.id = recommendations.consultation_id
      AND users.clerk_id = auth.uid()::text
    )
  );
```

### 3.2 Service Role Key 사용 보안

#### 사용 허용 범위

- 서버 사이드 API 엔드포인트에서만 사용
- 다음 경우에만 Service Role Key 사용:
  - 관리자 기능 (제품 크롤링 크롤링 업데이트)
  - 시스템 레벨 작업 (사용자 데이터 마이그레이션, 통계 집계)

#### 사용 금지 범위

- 클라이언트 코드
- 이미지 실행 코드
- `NEXT_PUBLIC_*` 환경변수

#### Service Role 사용 시 주의사항

1. **RLS 우회 가능**: Service Role 사용 시 RLS가 무시됨
2. **운영 권한 검증**: 코드 레벨에서 권한 검증 필요
3. **로깅**: Service Role 사용 시 로그 기록
4. **최소 권한**: 필요한 최소한의 작업만 수행

### 3.3 데이터베이스 접근 제어

#### 물리적 제어

- 프로덕션 DB 접근은 VPN 또는 IP 화이트리스트 가능
- DB 직접 접근은 관리자만 가능
- 모든 DB 접근 로그 기록

#### 백업 및 복구

- 일일 자동 백업
- 백업 파일 암호화 필요
- 백업 접근 권한 최소화

## 4. 개인정보 보호 정책

### 4.1 수집하는 개인정보

#### 필수 수집 항목

- **인증 정보**: Clerk를 통한 이메일, 이름
- **상담 기록**: 사용자 입력한 상담 내용, ICF 분석 결과
- **IPPA 결과**: 진행 필요성에 대한 정보, 제약 및 제한사항
- **추천 기록**: 추천된 제품 정보, 매칭 점수

#### 선택 수집 항목

- **피드백**: 상담 만족도, 개선 의견
- **사용 통계**: 페이지 접근, 기능 사용 기록

### 4.2 개인정보 수집 목적

1. **서비스 제공**: 맞춤형 제품 추천
2. **서비스 개선**: AI 모델 학습, 추천 정확도 향상
3. **통계 분석**: 서비스 사용 통계 분석 (익명화 처리)

### 4.3 개인정보 보관 기간

- **정상 사용**: 계정 삭제 전까지 보관
- **비활성 계정**: 마지막 로그인 후 3년 보관 후 삭제
- **법적 요구사항**: 법률 요구에 따라 필요한 기간 보관

### 4.4 개인정보 제3자 제공

#### 제공 대상

- **Google Gemini API**: ICF 분석을 위한 상담 내용 전송

  - **제공 항목**: 상담 내용, 진행 필요성 정보 (이름, 이메일 제외)
  - **목적**: AI 기반 ICF 코드 추출 및 맞춤형 제품 추천
  - **보관 기간**: Google 보안 정책에 따름 (사용자 데이터 암호화 전송 보장)

- **Supabase**: 사용자 데이터 저장 및 관리

  - **제공 항목**: 모든 사용자 데이터
  - **목적**: 사용자 데이터베이스 서비스 제공
  - **보관 기간**: 계정 삭제 전까지

- **Clerk**: 사용자 인증
  - **제공 항목**: 이메일, 이름
  - **목적**: 사용자 인증 및 세션 관리
  - **보관 기간**: 계정 삭제 전까지

#### 제공 제한

- 법적 요구사항 외 제3자 제공 금지
- 사용자 동의 없이 제3자 제공 금지

### 4.5 개인정보 익명화 및 가명처리

#### 익명/가명 처리 사용

- 이름, 이메일을 임시 ID로 대체

- **네이버**: naver Partners API 사용
  - 제품 링크 생성
  - 제품 정보 조회
  - API 이용약관 준수

#### 조건부 연동 (법적 검토 필요)

- **이미지 크롤링**: 공식 API 우선, 이미지 검색 크롤링 (법적 검토 필요)
- **기존 제품 링크**: 이전 크롤링한 제품 링크는 공식 제품 링크로 대체

#### 크롤링 제한

- robots.txt를 통해 크롤링 제한 명시적으로 설정
- 이용약관에서 명시한 크롤링 제한 명시적으로 설정
- 법적 검토 완료 후에만 진행

### 5.3 크롤링 실행 보안

#### 관리자 전용

- 크롤링 기능은 관리자(`role = "admin"`)만 실행 가능
- 모든 크롤링 실행 로그 기록

#### 실행 절차

1. **사이트 설정 확인**

   - `site-config.ts`에서 사이트 설정 확인
   - `enabled: false`인 사이트는 크롤링 제한

2. **robots.txt 확인**

   - 크롤링 전 robots.txt 확인 (운영 또는 개발)
   - Disallow 설정 준수

3. **요청 제한 준수**
   - 적절한 요청 제한 (Rate Limiting)
   - 서버 부하 최소화

### 5.4 제품 데이터 사용 보안

#### 수집 데이터

- 제품명, 가격, 이미지 URL, 링크
- 제품 분류, ISO 코드

#### 사용 범위

- 서비스 내에서만 맞춤형 제품 추천 목적으로 사용
- 직접 제품 데이터 수정 (수정 없이 조회)
- 외부 공개 명시 (필요한 경우)

#### 저작권 및 상표권

- 제품명, 이미지 URL은 해당 사이트의 저작권/상표권 준수
- 법적 문제 발생 시 즉시 중단 및 법적 검토

### 5.5 사이트별 설정 관리

#### site-config.ts 예시

```typescript
{
  name: "사이트명",
  baseUrl: "https://example.com",
  enabled: true, // 법적 검토 완료 여부
  legalReviewDate: "2025-01-23", // 법적 검토 완료일
  notes: "법적 검토 완료, 공식 제품 링크 계약 완료"
}
```

#### 법적 검토 프로세스

1. **1단계**: 사이트의 이용약관 및 robots.txt 검토
2. **2단계**: 법무팀과 검토 및 승인
3. **3단계**: 검토 완료 후 `enabled: true` 설정
4. **4단계**: 정기 보안 점검 (분기 1회)

   - 클라이언트 코드에 노출 금지

2. **프롬프트 입력 검증**
   - 사용자 입력 검증 및 필터링
   - 악의적 문자 데이터 처리

**전송 항목**:

- 상담 내용 (이름, 이메일 제외)

**전송 금지**:

- 이름, 이메일 주소
- 전화번호, 주소
- 피드백 내용 (제작은 제외)

#### 데이터 익명화

- 사용자 식별 정보 제거
- 개인 식별 가능한 데이터 마스킹
- 통계 집계 시 익명화 (필요한 경우)

### 6.3 전송절차 사용자 알림

#### 명시적 알림

모든 AI 관련 기능에서 다음 문구 표시:

> **필수 안내**
>
> 본 서비스는 AI를 사용하여 맞춤형 제품 추천 데이터 처리 서비스에 연동됩니다.
> 전송절차의 절차·조치에 대해 안내받지 못하셨다면 해당 서비스 설정은 거부하실 수 있으며 이에 대한 권리가 있습니다.

#### UI 표시

- 상담 시작 전에 알림 문구 표시
- 추천 결과 페이지에서 알림 문구 표시
- 사용자 확인 (체크박스)

### 6.4 AI 오류 및 한계 명시

#### 편향성 방지

- 다양한 사용자 그룹에 대한 편향적 추천
- 성별, 연령, 장애 유형에 따른 편향 최소화

#### 투명성

- AI가 추천한 이유 명시 (`match_reason`)
- ICF 코드 추출 과정 명시

#### 사용자 제어

- 사용자가 추천 결과에 대한 피드백 제공 가능
- 추천 만족도 조사 기능 제공

## 7. 로깅 및 모니터링 보안

### 7.1 로깅 분류

#### 최고 수준 로깅 (Error)

- 시스템 오류, 예외 발생
- **기록 항목**: 오류 메시지, 발생 시간, 접근 경로
- **기록 금지**: 사용자 이메일, 이름, 상담 내용 개인정보

#### 중간 수준 로깅 (Info)

- 일반적인 작업 로깅
- **기록 항목**: 작업 유형, 관련 ID, 사용자 ID (임시 ID)
- **기록 금지**: 개인 식별 정보, 비밀 데이터

#### 낮은 수준 로깅 (Debug)

- 개발/디버깅 목적
- **기록 항목**: 상세한 디버깅 정보
- **기록 금지**: 프로덕션 환경에서 사용 금지

### 7.2 로깅 보관 기간

- **일반 로깅**: 90일
- **오류 로깅**: 1년
- **보안 로깅**: 2년
- **디버깅 로깅**: 7일(로컬 환경만)

### 7.3 개인정보 마스킹

#### 로깅 생성 시 마스킹 절차

1. **이메일 주소 마스킹**

   - `user@example.com` → `u***@example.com`

2. **이름 마스킹**

   - `홍길동` → `홍**`

3. **전화번호 마스킹**

   - `010-1234-5678` → `010-****-5678`

4. **상담 내용**
   - 전체 상담 내용 로깅 금지
   - 필요한 경우 요약만 로깅

#### 로깅 마스킹 구현 예시

// lib/logging.ts에서 구현

  // 개인정보 마스킹 처리

## 8. 네트워크 보안

### 8.1 Next.js Middleware 보안

#### 인증 미들웨어

- 모든 보호된 경로에 Clerk 미들웨어 적용
- 공개 경로는 명시적으로 허용

#### matcher 설정

```typescript
export const config = {
  matcher: [
    // 정적 리소스 제외
    "/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)",
  ],
};
```

#### 주의사항

- API 경로가 예외로 처리되지 않도록 주의
- 정기적으로 matcher 검증 필요

### 8.2 공개 환경변수 (NEXT*PUBLIC*\*)

#### 사용 원칙

- 공개되어도 문제없는 정보만 사용
- 권한 제어는 RLS 및 JWT Claims로 처리
- 비밀키는 절대 `NEXT_PUBLIC_*`로 사용 금지

#### 공개 가능한 변수

- `NEXT_PUBLIC_SUPABASE_URL`: 프로젝트 URL
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`: 익명 키(RLS로 제어)
- `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`: 공개 키
- `NEXT_PUBLIC_APP_URL`: 애플리케이션 배포 URL
- `NEXT_PUBLIC_GA_MEASUREMENT_ID`: Analytics ID

### 8.3 클라이언트 사이드 데이터 보안

#### 데이터 전송 제한

- 비밀 데이터는 클라이언트 사이드에 전송 금지
- 필요한 최소한의 데이터만 전송
- 서버 사이드에서 데이터 마스킹

#### XSS 방지

- 사용자 입력 검증 및 이스케이프
- React의 기본 XSS 방지 기능 활용
- 외부 라이브러리 사용 시 보안 검토

## 9. 사고 대응 절차

### 9.1 비밀키 노출 대응

#### 즉시 조치 (1시간 이내)

1. 노출된 키를 즉시 비활성화/재생성
2. 관련 서비스에 통보 및 조치
3. 모든 환경에서 즉시 교체
4. 관련 서비스 제공자에 통보

#### 사후 조치 (24시간 이내)

1. 접근 로그 분석
2. 키 재설정 후 운영 재개
3. 보안 점검 수행
4. 사고 보고서 작성

### 9.2 데이터 유출 대응

#### 즉시 조치

1. 유출 경로 차단
2. 유출된 사용자 정보
3. 관련 서비스 제공자 및 사용자에 통보 (법적 요구사항 준수)

#### 사후 조치

1. 유출 원인 분석
2. 보안 강화 조치
3. 보안 정책 개선
4. 사고 보고서 작성

### 9.3 보안 취약점 발견 및 패치

#### 발견 절차

1. 보안 취약점은 해당 담당자에게 즉시 보고
2. 취약점 상세 정보 기록
3. 공개 보안 취약점은 공개

#### 패치 절차

1. 취약점 패치 우선순위 결정
2. 즉시 개발 및 테스트
3. 보안 강화 조치
4. 이후 로그 분석
