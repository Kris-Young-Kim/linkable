## 1. 환경변수 및 비밀키 관리

### 1.1 기본 원칙

- **절대 원칙**: 비밀키는 절대 Git 저장소에 커밋되어서는 안 됩니다.
- **최소 권한**: 각 키는 필요한 최소한의 권한만 부여받아야 합니다.
- **정기적 회전**: 비밀키는 정기적으로 회전(rotation)되어야 합니다.

### 1.2 비밀키 분류

#### 🔴 최고 민감도 (서버 전용, 절대 노출 금지)

- `SUPABASE_SERVICE_ROLE_KEY`: Supabase 서비스 롤 키
  - RLS를 우회할 수 있는 강력한 키
  - **사용 위치**: 서버 사이드 API 라우트에서만 사용
  - **절대 금지**: 클라이언트 코드, 브라우저, `NEXT_PUBLIC_*` 변수에 사용 금지

- `CLERK_SECRET_KEY`: Clerk 인증 서버 키
  - 사용자 인증 및 세션 관리
  - **사용 위치**: 서버 사이드에서만 사용

- `COUPANG_SECRET_KEY`: 쿠팡 파트너스 API Secret Key
  - API 서명 생성에 사용
  - **사용 위치**: 서버 사이드에서만 사용

- `GOOGLE_GENERATIVE_AI_API_KEY`: Google Gemini API 키
  - AI 모델 호출에 사용
  - **사용 위치**: 서버 사이드에서만 사용

#### 🟡 중간 민감도 (공개 가능하나 제한적 사용)

- `NEXT_PUBLIC_SUPABASE_ANON_KEY`: Supabase 익명 키
  - 클라이언트에서 사용 가능하나, RLS 정책으로 보호됨
  - **사용 위치**: 클라이언트 및 서버 모두 사용 가능
  - **주의**: RLS 정책이 제대로 설정되어 있는지 정기 점검

- `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`: Clerk 공개 키
  - 클라이언트 인증에 사용
  - **사용 위치**: 클라이언트에서 사용

- `COUPANG_ACCESS_KEY`: 쿠팡 파트너스 API Access Key
  - **사용 위치**: 서버 사이드에서만 사용 (Secret Key와 함께 사용)

#### 🟢 낮은 민감도 (공개 가능)

- `NEXT_PUBLIC_SUPABASE_URL`: Supabase 프로젝트 URL
- `NEXT_PUBLIC_APP_URL`: 애플리케이션 URL
- `NEXT_PUBLIC_GA_MEASUREMENT_ID`: Google Analytics 측정 ID

## 2. 인증 및 인가 정책

### 2.1 인증 (Authentication)

#### Clerk 인증 사용

- 모든 사용자는 Clerk를 통해 인증됩니다.
- 인증되지 않은 사용자는 다음 경로만 접근 가능:
  - 공개 페이지 (홈, 소개, 개인정보 처리방침)
  - 정적 자산 (이미지, CSS, JS)

#### 인증 미들웨어

- `middleware.ts`에서 모든 보호된 경로에 Clerk 미들웨어 적용
- 예외 경로는 명시적으로 정의되어야 함

### 2.2 인가 (Authorization) - 역할 기반 접근제어 (RBAC)

#### 역할 정의

| 역할 | 설명 | 권한 |
|------|------|------|
| `admin` | 시스템 관리자 | 모든 관리자 기능, 제품 크롤링, 사용자 관리, 통계 조회 |
| `manager` | 상담사/코디네이터 | 상담 데이터 조회/수정, 추천 관리, IPPA 평가 조회 |
| `user` | 일반 사용자 | 본인 상담 기록, 추천 결과, IPPA 설문 작성/조회 |

#### 기본 원칙: Deny by Default

- 역할이 없거나 미정의인 경우, 모든 관리자 API 및 민감 데이터 API 접근 거부
- 명시적으로 허용된 역할만 접근 가능

#### API 접근 제어 매트릭스

| API 경로 | admin | manager | user | 비고 |
|----------|-------|---------|------|------|
| `/api/admin/*` | ✅ | ❌ | ❌ | 관리자 전용 |
| `/api/admin/products/crawl` | ✅ | ❌ | ❌ | 제품 크롤링 |
| `/api/admin/products` | ✅ | ❌ | ❌ | 제품 관리 |
| `/api/analytics` | ✅ | ✅ | ✅ | 본인 데이터만 |
| `/api/consultations/*` | ✅ | ✅ | ✅ | 본인/담당 상담만 |
| `/api/recommendations/*` | ✅ | ✅ | ✅ | 본인/담당 추천만 |
| `/api/products/sync` | ✅ | ❌ | ❌ | 제품 동기화 |

#### 구현 요구사항

1. **`verifyAdminAccess` 함수**
   - Clerk 메타데이터에서 `publicMetadata.role` 확인
   - `role === "admin"`인 경우만 허용
   - 그 외 모든 경우 403 Forbidden 반환

2. **사용자 데이터 격리**
   - 모든 사용자 데이터 조회 시 `user_id` 또는 `clerk_id`로 필터링
   - 타인의 데이터 접근 시도 시 403 Forbidden 반환

3. **Clerk 메타데이터 관리**
   - 역할 변경은 관리자만 가능
   - 역할 변경 시 로그 기록
   - 역할 변경 프로세스 문서화

### 2.3 사용자 식별 및 매핑

#### Clerk → Supabase 매핑

- Clerk `userId`를 Supabase `users.clerk_id`와 매핑
- `ensureUserRecord` 함수로 자동 생성 시 기본 `role = "user"` 부여
- 역할 변경은 관리자만 가능

#### 데이터 소유권 검증

모든 데이터 조회/수정/삭제 시:

1. Clerk 인증 확인
2. Supabase users 테이블에서 내부 `user_id` 조회
3. 요청 대상 데이터의 `user_id`와 비교
4. 불일치 시 403 Forbidden 반환

## 3. 데이터베이스 보안 및 RLS

### 3.1 Supabase RLS (Row Level Security) 정책

#### 기본 원칙

- **모든 테이블에 RLS 활성화**
- **Service Role Key는 서버 전용**
- **클라이언트는 Anon Key만 사용**

#### 테이블별 RLS 정책

##### users 테이블

```sql
-- SELECT: 본인 데이터만 조회 가능
CREATE POLICY "users_select_own" ON users
  FOR SELECT USING (auth.uid()::text = clerk_id);

-- UPDATE: 본인 데이터만 수정 가능
CREATE POLICY "users_update_own" ON users
  FOR UPDATE USING (auth.uid()::text = clerk_id);
```

##### consultations 테이블

```sql
-- SELECT: 본인 상담만 조회 가능
CREATE POLICY "consultations_select_own" ON consultations
  FOR SELECT USING (
    EXISTS (
      SELECT 1 FROM users
      WHERE users.id = consultations.user_id
      AND users.clerk_id = auth.uid()::text
    )
  );

-- INSERT: 본인 상담만 생성 가능
CREATE POLICY "consultations_insert_own" ON consultations
  FOR INSERT WITH CHECK (
    EXISTS (
      SELECT 1 FROM users
      WHERE users.id = consultations.user_id
      AND users.clerk_id = auth.uid()::text
    )
  );
```

##### products 테이블

```sql
-- SELECT: 활성화된 제품은 공개 조회 가능
CREATE POLICY "products_select_active" ON products
  FOR SELECT USING (is_active = true);
```

##### recommendations 테이블

```sql
-- SELECT: 본인 상담의 추천만 조회 가능
CREATE POLICY "recommendations_select_own" ON recommendations
  FOR SELECT USING (
    EXISTS (
      SELECT 1 FROM consultations
      JOIN users ON users.id = consultations.user_id
      WHERE consultations.id = recommendations.consultation_id
      AND users.clerk_id = auth.uid()::text
    )
  );
```

### 3.2 Service Role Key 사용 정책

#### 사용 허용 위치

- 서버 사이드 API 라우트에서만 사용
- 다음 경우에만 Service Role Key 사용:
  - 관리자 기능 (제품 크롤링, 일괄 업데이트)
  - 시스템 레벨 작업 (데이터 마이그레이션, 통계 집계)

#### 사용 금지 위치

- 클라이언트 코드
- 브라우저 실행 코드
- `NEXT_PUBLIC_*` 환경변수

#### Service Role 사용 시 주의사항

1. **RLS 우회 인지**: Service Role 사용 시 RLS가 무시됨
2. **수동 권한 검증**: 코드 레벨에서 권한 검증 필수
3. **로깅**: Service Role 사용 시 로그 기록
4. **최소 권한**: 필요한 최소한의 작업만 수행

### 3.3 데이터베이스 접근 제어

#### 연결 관리

- 프로덕션 DB 접근은 VPN 또는 IP 화이트리스트 필수
- DB 직접 접근은 관리자만 가능
- 모든 DB 접근 로그 기록

#### 백업 및 복구

- 일일 자동 백업
- 백업 파일 암호화 저장
- 백업 접근 권한 최소화

## 4. 개인정보 보호 정책

### 4.1 수집하는 개인정보

#### 필수 수집 항목

- **인증 정보**: Clerk를 통한 이메일, 이름
- **상담 기록**: 사용자가 입력한 상담 내용, ICF 분석 결과
- **IPPA 평가**: 활동 중요도, 어려움 정도, 효과성 점수
- **추천 기록**: 추천된 보조기기, 클릭 이벤트

#### 선택 수집 항목

- **피드백**: 상담 만족도, 추가 의견
- **사용 통계**: 페이지 방문, 기능 사용 이력

### 4.2 개인정보 수집 목적

1. **서비스 제공**: 맞춤형 보조기기 추천
2. **서비스 개선**: AI 모델 학습, 추천 정확도 향상
3. **통계 분석**: 서비스 이용 현황 분석 (익명화 처리)

### 4.3 개인정보 보관 기간

- **활성 사용자**: 계정 삭제 시까지 보관
- **비활성 사용자**: 마지막 접속 후 3년 보관 후 삭제
- **법적 요구사항**: 관련 법령에 따라 필요한 기간 보관

### 4.4 개인정보 제3자 제공

#### 제공 대상

- **Google Gemini API**: ICF 분석을 위한 상담 내용 전송
  - **제공 항목**: 상담 내용, 활동 정보 (이름, 이메일 제외)
  - **목적**: AI 기반 ICF 코드 추출 및 보조기기 추천
  - **보관 기간**: Google 정책에 따름 (데이터 비학습 옵션 사용 권장)

- **Supabase**: 데이터 저장 및 관리
  - **제공 항목**: 모든 사용자 데이터
  - **목적**: 데이터베이스 서비스 제공
  - **보관 기간**: 계정 삭제 시까지

- **Clerk**: 사용자 인증
  - **제공 항목**: 이메일, 이름
  - **목적**: 사용자 인증 및 세션 관리
  - **보관 기간**: 계정 삭제 시까지

#### 제공 금지

- 마케팅 목적의 제3자 제공 금지
- 사용자 동의 없이 제3자 제공 금지

### 4.5 개인정보 익명화 및 가명화

#### 연구/통계 목적 사용 시

- 이름, 이메일, Clerk ID 제거

#### ⚠️ 조건부 허용 (법무 검토 후)

- **네이버 쇼핑**: 공식 API 우선, 부재 시 스크래핑 (법무 검토 필수)
- **기타 쇼핑몰**: 사전 서면 동의 또는 공식 제휴 계약 후 허용

#### ❌ 금지

- robots.txt에서 크롤링 금지 명시된 사이트
- 이용약관에서 무단 크롤링 금지 명시된 사이트
- 법무 검토 미완료 사이트

### 5.3 크롤링 실행 정책

#### 관리자 전용

- 크롤링 기능은 관리자(`role = "admin"`)만 실행 가능
- 모든 크롤링 실행 시 로그 기록

#### 실행 전 검증

1. **사이트 상태 확인**
   - `site-config.ts`에서 사이트 설정 확인
   - `enabled: false`인 사이트는 크롤링 금지

2. **robots.txt 확인**
   - 크롤링 전 robots.txt 확인 (수동 또는 자동)
   - Disallow 규정 준수

3. **요청 빈도 제한**
   - 과도한 요청 방지 (Rate Limiting)
   - 적절한 딜레이 적용

### 5.4 데이터 사용 정책

#### 수집 데이터

- 제품명, 가격, 이미지 URL, 구매 링크, 설명
- 제조사, 카테고리, ISO 코드

#### 사용 범위

- 서비스 내 보조기기 추천 목적으로만 사용
- 원본 데이터 보존 (수정 없이 표시)
- 출처 명시 (가능한 경우)

#### 저작권 및 상표권

- 제품명, 이미지는 원본 사이트의 저작권/상표권 존중
- 상업적 이용 시 라이선스 확인 필수
- 분쟁 발생 시 즉시 중단 및 법무 검토

### 5.5 사이트별 설정 관리

#### site-config.ts 구조

```typescript
{
  name: "사이트명",
  baseUrl: "https://example.com",
  enabled: true, // 법무 검토 완료 여부
  legalReviewDate: "2025-01-23", // 법무 검토 완료일
  notes: "법무 검토 완료, 공식 제휴 계약 체결"
}
```

#### 법무 검토 프로세스

1. **1단계**: 사이트 이용약관 및 robots.txt 검토
2. **2단계**: 법무팀 검토 요청
3. **3단계**: 검토 완료 후 `enabled: true` 설정
4. **4단계**: 정기 재검토 (연 1회)

## 7. 로그 및 모니터링 정책

### 7.1 로그 분류

#### 🔴 에러 로그 (Error)

- 시스템 오류, 예외 발생
- **포함 가능**: 에러 메시지, 스택 트레이스, 요청 경로

#### 🟡 정보 로그 (Info)

- 일반적인 작업 로그
- **포함 가능**: 작업 유형, 타임스탬프, 사용자 ID (해시값)
- **포함 금지**: 개인 식별 정보, 민감 데이터

#### 🟢 디버그 로그 (Debug)

- 개발/디버깅 목적
- **포함 가능**: 제한적 디버그 정보
- **포함 금지**: 프로덕션 환경에서 사용 금지

## 8. 프론트엔드 보안

### 8.1 Next.js Middleware 보안

#### 인증 미들웨어

- 모든 보호된 경로에 Clerk 미들웨어 적용
- 예외 경로는 명시적으로 정의

#### matcher 설정

```typescript
export const config = {
  matcher: [
    // 정적 자산 제외
    '/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)',
  ],
}
```

#### 주의사항

- API 경로가 실수로 예외에 포함되지 않도록 주의
- 정기적으로 matcher 패턴 검증

### 8.2 공개 환경변수 (NEXT_PUBLIC_*)

#### 사용 원칙

- 공개되어도 안전한 값만 사용
- 권한 제어는 RLS 및 JWT Claims로 처리
- 비밀키는 절대 `NEXT_PUBLIC_*`로 사용 금지

#### 공개 가능한 변수

- `NEXT_PUBLIC_SUPABASE_URL`: 프로젝트 URL
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`: 익명 키 (RLS로 보호)
- `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`: 공개 키
- `NEXT_PUBLIC_APP_URL`: 애플리케이션 URL
- `NEXT_PUBLIC_GA_MEASUREMENT_ID`: Analytics ID

### 8.3 클라이언트 사이드 보안

#### 데이터 노출 방지

- 민감 데이터를 클라이언트에 전송하지 않음
- 필요한 최소한의 데이터만 전송
- 서버 사이드에서 데이터 필터링

#### XSS 방지

- 사용자 입력 검증 및 이스케이프
- React의 기본 XSS 방지 기능 활용
- 외부 라이브러리 사용 시 보안 검토
